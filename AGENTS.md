# Domos

Domos provides persistent AI companions with memory, tools, and computer-owned workspaces.
Users choose their models and deployment: local, self-hosted, or cloud.
Pi Durable 1.4.0 stores Bot tasks. Native Harness processes own model loops. Domos owns product capabilities.

## Architecture and ownership

- Each Domos computer owns its Bots, chats, memories, routines, and files. Clients access that computer. Switching computers does not move Bots. Scope client caches and drafts by the persisted computer identity. Keep one desktop window and one active workspace view. Preserve each address's session partition. Commit a switch after authorization and saved selection succeed. Release old subscriptions and viewer leases. Retain contacts, drafts, reading anchors and inspector state by computer.
- New Bots use their owning computer and get a persistent personal directory. System tool access still requires authorization. A Bot can select an existing project directory while idle. Native sessions distinguish project directories. Preserve each attachment's source directory.
- Local Docker containers are advanced execution environments on the owning computer. Commands, files, MCP, browser, and desktop use the same selected environment. Do not create new cross-host bindings. Retain existing remote and container bindings, volumes, files, and accounts until an explicit migration.
- Docker releases bind desktop packages to image digests in release.json. Release CI builds and tests images before packaging. LocalStack owns backend readiness and stopped-data upgrade snapshots. Keep task admission closed until upgrade checks pass. Preserve existing work environments until a confirmed idle rebuild. See [Docker releases](docs/docker-release.md).
- Domos owns Bot identity, full chat history, memories, and computer permissions. Native Harness accounts use the work computer's OS user and configuration. Preserve retained service credentials during migration.
- Memory records belong to one Bot unless the user shares them. Keep profile snapshots stable for each Durable task. Send changed snapshots to retained native sessions on their next task. Route manual, Agent and review writes through the shared memory service. Verify original evidence and keep inference distinct from user facts. Background review uses a separate native session every ten turns. It saves clear sourced facts and updates automatic records in place by ID and revision. It silently skips manual, deleted, stale and uncertain records. Keep questions and approval queues out of upkeep. Version checks and source tombstones block stale writes and deleted-source extraction. Missing provenance stays missing. Profile snapshots contain only IDs and facts; read provenance on demand. Preserve original chat when updating or deleting memory. See [memory evals](docs/memory-evals.md).
- Grok uses the installed native CLI through ACP. Additional input uses its native interjection request with stable message identity. Antigravity uses native ACP prompt replacement only on supported versions. Devin uses its declared mid-turn capability. Cursor uses native ACP and queues additional input for the next turn. Prompt completion waits for all admitted prompts and records terminal usage once. Single approvals cannot enable Devin bypass. Shared ACP transport and OpenCode history have separate owners. Retain native context readings, cumulative costs and readable compaction summaries. Unknown values stay unknown. Read native MCP catalogs without copying credentials.
- Antigravity 1.5+ reports uncached input separately from cache reads. Its injected MCP servers use deferred exposure in the existing stdio bridge. Keep original tool authorization, arguments, results and cancellation. Usage settlement has its own transaction; accounting failures warn without changing confirmed task results.
- Durable owns input admission and persistent tasks. Native Harness processes own generation and model context. Adapters coordinate cancellation and recovery through public protocols. Observe uncertain results before more mutations.
- Reuse the work computer's CLI before installing a version in its Domos runtime directory. Inspect, login, and execute with the same program and OS user. Switch programs and Harness only while the Bot is idle.
- Retain compatible Codex, Claude, Pi, Grok, Antigravity, Devin and Cursor connections between chat turns. Bind task callbacks per turn. Close idle connections on configuration or directory changes and after ten minutes. Stop terminates the active process tree. See [Harness context](docs/harness-context.md).
- Bot approval modes live in EngineConfig. Expose only supported modes. Map them to native Harness permissions. Full access alone answers remaining eligible permission requests automatically. Keep questions, computer authorization, MCP grants, cancellation, and OS restrictions. Changing permissions uses a separate native session. Keep existing automatic approval behavior until the user selects a unified mode.
- Native CLI transports own model HTTP. Use Photon and model image limits at the attachment boundary. Preserve original evidence and include coordinate mapping when resizing observations.
- Keep system instructions stable across tool rounds. Read current time through routine_list. Bound tool images in model requests while retaining full evidence and user attachments. See [Harness context](docs/harness-context.md).
- Send chat, additional input, routines, API calls, CLI calls, and peer requests through Runtime.submit. Keep request IDs stable through retries.
- Send standalone CTA messages through the shared send_link_card product tool. Preserve authored text, stable message identity and receipt order. Cards do not wait for an answer. Read website previews only for visible cards through Files. Bound HTTPS reads, validate socket addresses and redirects, and reuse image workers and caches. Open links only on user action through the existing external-link boundary.
- Bot sessions record their owning Bot and purpose. Private, team, and delegated sessions keep separate native contexts. Team members retain their own Harness, tools, memory, and permissions. Share explicit task materials through Files. Durable waits for delegated native turns and their subtasks, then returns results to the source session. Stop follows these task relationships and leaves other sessions intact.

Keep delegated contexts and other members' raw tool results private. Handoff excerpts retain source IDs and truncation bounds; search indexes remain rebuildable.

Keep native summary boundaries separate from Domos entry cursors. Dispatch rebuilt sessions directly with available summaries and bounded recent original messages. Keep built-in MCP ownership by excluding replacement extensions within that process; never persist those exclusions to user settings. Registration-time side effects remain outside lifecycle filtering. Native tool_search loads their schemas. Read [Harness context](docs/harness-context.md) before changing tool bridges or readiness checks.

Native session compatibility includes their schemas and shared guidance. Keep uncertain outcomes behind the existing recovery boundary. Link previews resolve synthetic DNS through pinned HTTPS DNS, then connect only to checked public addresses. Stop HTML reads at the head boundary. Cache successful and genuinely empty previews. Link cards show a themed default cover until a preview image loads. Empty, failed and blocked previews retain that cover without error controls.

## Computer Use contracts

- Reuse Cua for desktop execution and the existing browser service for DOM/CDP operations. Keep platform details at these boundaries.
- Read native desktop catalogs independently of screenshot capture. A failed screenshot does not remove other desktop tools. Browser catalogs and native batches share one management boundary; native protocols own ordinary operation names and arguments.

Keep the identity header fixed across Bot, Computer, Browser, and Work tabs. Use the native Fullscreen API for the screen and toolbar. See [Browser Use](docs/browser-use.md).
- Expose native desktop actions, batches, and scripts with their original parameters. The Agent selects the tool and requests observations. Check a state transition before dependent actions.
- Keep desktop operation guidance in shared computer instructions. Computer boundary sections report environment and permissions. Native schemas and get_guide own syntax. Keep window focus separate from action delivery mode. Match snapshot controls to the intended role and label.
- Bind actions and observation to the same confirmed target. Cua owns native sessions. Forward the Agent's parameters unchanged. Discover a new target when a dialog or window changes.
- Distinguish action delivery, action verification, observation, and user-task completion. A successful call or screenshot alone does not prove task completion.
- If an action ran but observation failed, preserve the execution record and recover observation. Do not replay an action whose outcome is uncertain.
- Preserve the saved native tool catalog, including output schemas and annotations. Deliver structured metadata in supported text content and retain screenshots with their current coordinates. Put Domos status outside strict native structured output.
- Preserve cancellation for direct actions, batches, and scripts. Request observation explicitly when an outcome is unknown.
- Preserve approval, cancellation, and user takeover on every execution path, including Jev assistance.
- Route ordinary computer mutations through the shared approval callback. Browser observation tools use an explicit allowlist; arbitrary JavaScript requires approval.
- Keep dispatched browser work alive until it settles. Cancel queued work. Preserve the page during takeover. Persist uncertain mutations across worker restarts, and require explicit browser restart before more mutations. Observation failures preserve their error and do not create or clear mutation barriers. Reconnect a closed MCP transport without closing Chrome.
- Share control between a headed browser and its desktop. Isolate control only after the worker confirms a headless browser. Wait for human input to finish before returning control.
- Route Agent handoff requests through the shared `computer_request_takeover` tool and stored chat cards. Complete only the live request whose viewer owns control. Closing a viewer does not complete a request.
- Reserve a viewer's lease before takeover waits. Keep its frames and acknowledgements live during the grant. Allow input only after the grant completes. Reuse concurrent requests from that viewer and release its reservation when it closes.
- Browser actions return native results. The Agent chooses observations, native condition waits and `agent_browser_batch`, including its bail option. Use `agent_browser_observe` after takeover or unclear screenshots. Preserve delivered actions when observation fails. Do not infer missing-content causes from blank space or document readiness.
- Browser mode belongs to the shared work-browser service. Change it only through a confirmed restart. Reuse the Bot profile. Hold browser and desktop control during the change. Report observed access evidence; do not hardcode website fallbacks or open personal browsers.
- Browser preparation reads the native page address. Keep window resizing out of readiness checks. Open the native viewport stream only for viewing. A viewer failure does not change DOM tool availability.
- For viewer input, layout, or reconnect changes, follow [docs/browser-use.md](docs/browser-use.md). Test clicks through the scaled image and read back the real page. Scripted focus and mocked RPC output do not verify takeover.
- Preserve native action results when observation or evidence storage fails. Keep runtime browser arguments in Domos, and apply text limits at the browser boundary. See [docs/browser-use.md](docs/browser-use.md).
- Cua sessions own desktop cursors and motion. Use the native cursor renderer and timing. Select a native theme from the current Bot avatar color. Retain the native soft glow and reduced-motion policy.
- Track physical pixels, logical points, and screenshot coordinates explicitly at input and viewing boundaries.

## Verification

- Use the scripts in `package.json` as the command source. Run focused tests for the changed behavior first, then the checks required by affected consumers and CI.
- Group web and API tests by feature ownership. Extend the relevant suite. Web suites share the per-test service fixture in `apps/web/test/fixtures/service.ts`; API suites share `apps/api/test/fixtures/api.ts`. Keep feature assertions in their suites and preserve isolated data and service cleanup.
- Run `pnpm typecheck` and `pnpm lint` for code changes. Fix new errors and report retained warnings.
- For Harness or Computer Use changes, read [docs/computer-evals.md](docs/computer-evals.md) before changing behavior. Save the relevant failure or baseline first. Run the regression after the change.
- Add new confirmed failure cases to the small, sanitized eval set. Report completion evidence, coverage, elapsed time, and model round trips when available. Without eval evidence, do not claim a Harness performance or success-rate improvement.
- Offline trajectory scoring evaluates recorded behavior. Scorer tests test the scorer. Neither reruns an Agent. Rule pass rates are separate from task success rates.
- Verify visible UI changes in the running UI. Use real input and result readback for native input claims; simulated protocol tests are not native desktop acceptance.
- Wait for a state or event in tests. Use timeouts as hang guards. Keep a performance threshold tied to the work it measures and report runner limits.
- For cross-platform claims, inspect Windows, Linux, and macOS results for the same commit in `.github/workflows/checks.yml` and `.github/workflows/computer-input.yml`.
- Checks owns change selection and test partitions in `.github/ci.mjs`. Run platform-independent regressions, lint and typecheck once on Linux. Daily full Web E2E uses two Linux shards. Selected native process, browser and input checks retain Windows, Linux and macOS coverage. Run Harness process tests and real browser service tests in separate sequential steps. Use the runner default shell for native process tests. Each runner uses one GUI worker. Daily desktop smoke covers startup, connection, chat and exit. Relevant desktop, runtime, asset or dependency changes select full desktop and Windows packaging with the packaged identity test. Select Docker and SSH by their affected boundaries. Manual Checks and `v*` tags run full validation. New runs cancel older runs for the same workflow and ref.
- Report skipped and untested capabilities explicitly. Green CI does not prove every OS permission, desktop session, or third-party application works.
- Documentation-only edits need link, path, and diff checks. Do not add tests that assert document wording.
- Main pushes and pull requests always produce a Checks result. Changes limited to root `AGENTS.md`, root `README*.md`, and Markdown under `docs/` omit product jobs. Dependencies, shared configuration, unknown paths and unavailable Git comparisons select full validation. The result job distinguishes scope omissions from failed or cancelled checks. Verify added, deleted and renamed paths when changing selection rules.

- Windows development and packaged builds use separate stable App IDs. Verify the registered application target as well as the window icon.
- LocalHost owns native service readiness, exit and recovery. Publish service state through the validated desktop bridge. Limit automatic recovery to two attempts and two restarts per minute. Stop, maintenance and inactive workspace selection disable automatic recovery. Reuse the data lease and native task recovery; service restart does not resubmit tasks. Keep bounded diagnostic files with process identity, exit codes, error types and code locations. Exclude dialogue, credentials and tool payloads.
- Show connection and read failures through the shared application Toast owner. Keep one workspace connection notice. Preserve content and drafts while disconnected. Hide stale live activity until subscriptions return. Keep task failures in their saved records and field validation beside its input.
- Preserve user data and existing public contracts. Keep authentication, authorization, IPC validation, Electron sandboxing, and context isolation at their boundaries.
- Bind local desktop authorization to the saved instance ID through parent IPC or the private desktop credential. Renew the same grant. Keep native and Docker identities separate. Historical grants need explicit revocation; labels do not identify devices. Device activity uses bounded writes. Direct pairing verifies the configured HTTPS origin against the persisted computer identity. Keep the loopback desktop origin usable. Share one-time codes in URL fragments and exchange them only after confirmation. Settings owns device connection and login detail navigation.
- DirectConnection owns the saved network origin in HostingStore. Use publicUrl only until a connection choice is saved. Verify HTTPS and computer identity before switching origins. Native Tailscale setup owns only its confirmed Serve listener; retain user-owned routes and refuse public Funnel addresses. Detect Tailscale on connection-page requests. Docker uses a host-configured HTTPS address. Keep network setup outside desktop startup.
- Restart only identified Domos processes. Check PID, executable path, and ownership before stopping them. Do not kill all Electron processes or an entire tree that may contain user applications.
- Use a small test window for desktop checks when possible. Use the user's requested application only within the authorized task.

- Create feature branches from the latest `main`. Develop and commit in the existing repository directory, one feature at a time.

- Push when authorized by the user. Verify the merged commit and all required CI results.
